virtual memory (a sandbox of memory for a process) is implemented by both **hardware: MMU (memory management unit)** and software **(operating system)**

every program gets it's own **virtual address space** which makes them believe they have their own contiguous block of memory.

`int x = 40` -> when you do this, your CPU generates a virtual memory address which has to map to a physical memory address, the MMU does precisely that. It looks at the page table, and if it exists in physical memory, it returns precisely the value stored in that part of physical memory.

a virtual address is broken down into 2 parts:

- Virtual page number -> which page (physical)?
- Offset -> (where inside of the page?)

The MMU translates this virtual page number into a physical frame number. The offset remains unchanged as it's supposed to be a reflection of the physical memory.

the TLB is a cache inside the CPU so that the MMU does not have to walk the page table (in main memory) each time.

> The goal of virtual memory is to map virtual memory addresses generated by an executing program into physical addresses in computer memory.

> This concerns two main aspects: **address translation (from virtual to physical)** and **virtual address spaces management**

Virtual address spaces management is done by the OS, while **address translation** is done by the CPU.

virtual memory provides better security because of memory isolation, frees programmers and applications from having to worry about managing shared memory; and allows programs to **use more memory than is physically present on the machine via paging**.

almost every virtual memory implementation divides the virtual address space into **pages** (contiguous blocks of virtual memory addresses) which are usually **4Kb** in size.

The **MMU** uses a **page table** (a data structure in the operating system) to translate virtual memory addresses to physical memory addresses.

> Concretely, the MMU stores a _cache_ of recently used mappings out of those stored in the whole OS page table, which is called **Translation Lookaside Buffer** (**TLB**).

> When a virtual address needs to be translated into a physical address, the MMU first searches for it in the TLB cache (**step 1.** in the picture above). If a match is found (i.e., _TLB hit_) then the physical address is returned and the computation simply goes on (**2.a.**). Conversely, if there is no match for the virtual address in the TLB cache (i.e., _TLB miss_), the MMU searches for a match on the whole page table, i.e., _page walk_ (**2.b.**). If this match exists on the page table, this is accordingly written to the TLB cache (**3.a.**). Thus, the address translation is restarted so that the MMU is able find a match on the updated TLB (**1** & **2.a.**).

^ check TLB first, if not in TLB, go to whole page table, and if its there, add it to the TLB.

> Unfortunately, page table lookup may fail due to two reasons. The first one is when there is no valid translation for the specified virtual address (e.g., when the process tries to access an area of memory which it cannot ask for). Otherwise, it may happen if the requested page is not loaded in main memory at the moment (an apposite flag on the corresponding page table entry indicates this situation). In both cases, the control passes from the MMU (hardware) to the page supervisor (a software component of the operating system kernel). In the first case, the page supervisor typically raises a segmentation fault exception (3.b.). In the second case, instead, a page fault occurs (3.c.), which means the requested page has to be retrieved from the secondary storage (i.e., disk) where it is currently stored. Thus, the page supervisor accesses the disk, re-stores in main memory the page corresponding to the virtual address that originated the page fault (4.), updates the page table and the TLB with a new mapping between the virtual address and the physical address where the page has been stored (3.a.), and finally tells the MMU to start again the request so that a TLB hit will take place (1 & 2.a.).

page lookup/walk (step 2, done by the MMU) may:

- succeed (page hit), adds the address to main memory where it needed to be accessed
- page fault (goes and looks it up in secondary storage, disk, where it then places it to the page table, main memory, and the TLB)
- segmentation fault (the program cannot access that area of memory)

> As it turns out, the task of above works until there is enough room in main memory to store pages back from disk. However, when all the physical memory is exhausted, the page supervisor must also free a page in main memory to allow the incoming page from disk to be stored. To fairly determine which page to move from main memory to disk, the paging supervisor may use several **page replacement algorithms**, such as **Least Recently Used** (**LRU**). Generally speaking, moving pages from/to secondary storage to/from main memory is referred to as **swapping** (**4.**), and this is why page faults may occur.

the reason why page faults occur is that not all pages can be stored in main memory. This is what **swap memory** on disk is for. so that we can store pages on disk to be then put on the paging table.

There are different page replacement algorithms, such as **Least Recently Used**

# The seperation of OS and user mode virtual memory

This is the usual memory layout of a Linux process running on a 32 bit CPU architecture.
![Process memory layout](./imgs/Pasted%20image%2020261119185632.png)

The OS (kernel space) part of the memory a process always assumes the same virtual address space (from 0xFFF... to 0xC000... basically $2^{32}$ bytes). That is why a pointer in a 32 bit system is of size 2^32 (one number for each memory address, as memory is addressed in bytes)

If only 512MB of memory out of 1GB is available on the physical machine, then 512MB out of the virtual address space will be mapped while the rest 512MB of memory will be left unmapped. If the system has 2GB of available physical ram then the whole 1GB will be mapped to the kernel and the rest shall be free for user space use.

You could potentially use virtual memory and keep some of the pages of the kernel on disk, but that would be extremely foolish as you might even fail to use the page intended for the code (OS page supervisor) which is responsible for generating page faults!

That is why all kernel code is must be in the main memory page table at all times. This shouldn't be that hard as most distros have an average usage of 128mb-256mb (I checked that from google `2026-11-19 21:13 64 bit architecture`).
